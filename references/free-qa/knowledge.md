## 一、能力边界（老板问「能做什么 / 能算什么」时按这张表展开，不许自拟）

| 维度 | 实际覆盖 |
|---|---|
| **商品** | 商城商品码、商品名称、类目、流通/非流通品 |
| **供商** | 供商名称（数量随每日快照变动，**不要向老板报具体家数**；自营品统一显示「没有供商」） |
| **库存** | 每日库存快照、当前件数、在售/已断（`is_sold_out`） |
| **销量** | 订单明细：按日、按商品、成交价×数量=销售额；订单历史可回溯约 3 年 |

**能算出来的指标**（这是"推理"的真实边界，别超）：日均销量（剔除塌陷日）、可售天数、预计断货区间、3 天缺口、ABCD 等级（按历史月销额）、已有库存记录内的售罄天数、连续缺货天、供商集中度、类目结构、增速比。

> ⚠️ 「售罄天数」只能算到库存记录覆盖的日期为止（快照从 2026-11-03 起累积）。**不要向老板承诺「近 30 天」**——天数不够时如实说「记录只有 N 天，先按这段算」。

**四张表**：①谁已经卖断了 ②谁卖得又快又多 ③谁还有货但快撑不住 ④哪个供商在缺货。

**明确不能做（防止吹牛，被问到必须如实说）**：

- 只读，**不能改任何数据**
- 不能报"准确断货日"，只能给**区间**并按紧急度排序——模型对边卖边补的品会失效
- **不知道**供商到货周期（库里没有采购单/入库流水表，推不出「下单后几天到」）
- 起订量 **有**：`item_sale.moq` 与 `order_limit`（实测 14,283 个在售品 100% 有值），但只知道「一次最少订多少」，不知道补货要等多久
- **覆盖不到**多数云仓供商的可售天数（库存写 `10000` 占位，算不出来），这部分看 ① 和 ④
- 不是"通用 AI 助手"，就是这 4 张表 + 只读追问，别把自己说大

> 口径问题（这个数怎么算的、能不能自己定标准）→ 见 `gate.md` 第六节。

## 二、业务常识（读报表前必知 · 老板口述口径，禁止当脏数据）

以下三条是**业务模式**造成的，不是数据错误。任何报表、任何解读、任何备注，都不得把它们当异常处理。

### 1. 云仓商品 · 库存数字特别夸张

- 可售天数 / 库存量夸张到不合理（1,300 天、1,400 天、上千万天这种）的品，**基本是云仓商品**。
- 云仓的供货模式是**「要么有货就很多很多，要么直接无货」**，不是均匀消耗；库存不会渐进下滑，断货是断崖式的。
- 因此：① 不能判为数据错误；② **不能标「库存疑占位」这类暗示数据造假的措辞**；③ 也不能按常规备货节奏说它"快断了"——它给不出渐进的预警信号。
- 需要标注时统一写「**云仓（有货量大 / 无货即断）**」；可售天数照实显示，不截断、不特殊处理。

**数据事实（2026-11-08 实测，可直接引用）**：云仓的库存字段**并不记录真实件数**，绝大多数行直接写 `10000` 整值。

- 全站 89 家供商，只有 **2 类**是真件数：北京百世鼎盛（7,244 键 / 469 种取值 / `10000` 占位率 0.5%）、自营 `provider_id=0`（1,410 键 / 480 种取值 / 0.8%）
- 其余 87 家的 `10000` 占位率：北京悦诺 74.5%、北京首盛 73.9%、北京国兴添乐 55.7%、北京味聚德 40.0%
- 后果：这些供商的可售天数会算成 1,500~3,000 天，任何「可售 ≤N 天」的预警规则都会把它们**整体排除**——这是**漏报**，不是误报；看到"名单只集中在 1~2 家供商"时，先按占位率排查，不要先怀疑关联键或清洗 bug
- **判据**（复用即可）：某供商库存唯一取值数 < 50 或 `10000` 占位率 > 5% → 判不可信，不进按天数的预警
- 反过来，`is_sold_out` 才是云仓唯一可靠的判据——所以 ① 卖断货、④ 供货缺货不受影响，仍能覆盖全部供商

### 2. 无供商商品 = 自营商品

- `provider_id` 为空、上架供商为 0 的商品，业务上属于**自营商品**（自家经营，非外部供货商供货）。
- **报表展示仍写「没有供商」**（留空或「—」），**不要改写成「自营」**——老板要的是这个直白说法。
- 但解读时必须清楚：它**没有供商可催**，缺货只能靠自家采购/调拨解决。
- **不要为自营商品单独写死一套话术**：「建议动作」列统一按缺货天数给动作（当天缺货 → 优先补货/催供；连续 N 天 → 连续缺货 N 天，优先补货/催供），**不要**因为供商为空就换成「自营商品，走内部采购/调拨」。
- 标注只做一处：**供商列写「没有供商」**，表结构、列数、JSON 元数据一概不动。
- ④ 供货缺货里的「供商 0 行」就是这批自营商品的真实库存，**判定规则不变**（供商 0 行还有货 → 整件没断、不计入、不归任何供商）。

### 3. 支付 · 未支付是常态，不是欠款风险

实测近 30 天 62,592 张有效单：

| 项 | 实测 | 说明 |
|---|---|---|
| `pay_type=1` 货到付款 | 59,492（95.1%） | B 端批发主流，先发货后收款 |
| `pay_type=3` 账期赊销 | 3,100（5.0%） | 只有这类才走线上支付 |
| `pay_status=1` 未支付 | 49,816（79.6%） | **货到付款模式下的正常状态** |
| 有 `pay_time`、`actual_pay_amount` | 仅 3,099（5.0%） | **只有 5% 的订单有支付记录** |

**三条铁律**：

- **绝不把「未支付 79.6%」当异常或资金风险报给老板** —— 这是生意模式，不是漏洞
- **绝不拿 `actual_pay_amount` 当营收/回款口径** —— 它只覆盖 5% 的订单，用它算总额会小 20 倍
- **不做应收应付、账期回款、对账核销** —— 系统里没有这些数据，算不了

### 4. 仓储 · 只有仓库标签，没有仓储作业

- `inventory_daily_detail.dc` 实测只有 **2 个仓**；`order_head.warehouse_code` 也只有 2 个取值
- 有 `storage_type`（仓储类型）、无入库/出库/库位/批次/调拨
- **不做**：库位管理、出入库流水、批次效期管理、盘点差异

### 5. 完全没有的领域（老板问起直接说"做不了"）

排货、配送路线（排线）、运输时效、司机、车辆调度、承运商 —— 一条数据都没有，**不要顺着老板的话编**。

> 业务常识随老板口述持续补充。**每一条新增业务知识都必须落到本文件**，不许只留在对话里或记忆里。
