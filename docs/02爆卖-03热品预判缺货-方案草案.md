# ② 爆卖 · ③ 热品预判缺货 · 方案草案（待反向验证）

> 状态：方案待验证，未开发、未跑数。
> 用途：交 Cursor 侧做可行性反向验证。
> 定稿后并入 `SKILL.md` 的 ②/③ 章节，样式沿用 `references/style-contract.md`。

## 一、两张表的性质区分

② 和 ③ 必须分成两个独立产物，因为一个是描述现状、一个是预测行动，不能合成一个 sheet 的上下两页。

| | ② 爆卖 | ③ 热品预判缺货 |
|---|---|---|
| 性质 | **描述现状**：现在卖得多不多、在不在涨 | **预测未来**：明天还有没有货可卖 |
| 主判据 | 加速比（近3日均 ÷ 前4日均） | 可售天数（库存 ÷ 日均销量） |
| 受众 | 运营 | 采购 |
| 动作 | 加推、给流量、加采购计划 | 今天下单、提前和供商沟通 |
| 时效 | 每天看趋势 | 当天必须处置，晚一天就丢销量 |
| 产物 | `02-爆卖-热度攀升_YYYYMMDD.xlsx` | `03-热品预判缺货_YYYYMMDD.xlsx` |

## 二、共享热品池（关键，不是子集关系）

两张表都从同一个**热品池**出发，再按不同方向筛：

```
热品池 = 近7日销量 ≥ 10 件 且 当日未断货 的在售品
   ├─ ② 爆卖    = 热品池 ∩ 在涨（按规模分三档加严，见第四节）
   └─ ③ 预判缺货 = 热品池 ∩ 撑不住（可售天数 ≤ 阈值）
```

**两者是交叉关系，不是包含关系。** 交集是「又涨又快断」，这是最高优先级，两张表都会出现。

必须避免的逻辑漏洞：销量稳定、不涨但消耗极大的品（例：稳定日销 300 件、库存仅够 2 天）**不会出现在 ②**（它不暴涨），但**必须出现在 ③**（它马上就要断）。若按「③ 是 ② 子集」设计，这类品会被整体漏掉。

## 三、数据源与关联键（已实测）

| 用途 | 表 | 关键字段 |
|---|---|---|
| 销量件数 | `dmall_saas_oms.order_detail` | **`sku_code`（= 商城商品码 item_id）**、`quantity`、`order_code` |
| 订单有效性 | `dmall_saas_oms.order_head` | `order_time`（Unix 秒）、`valid=1` |
| 当前库存 | `dmall_saas_atp.inventory_daily_sale` | `snapshot_date`、`item_id`、`provider_id`、`total_qty`、`is_sold_out`、`zone_code` |
| 商品信息 | 商品库 `item_sale` | `item_id`、`name`、`provider_id`、`status=2`、`sale_type=1` |
| 类目 | `item_sale` → `goods`（`DISTINCT item_id`）→ `item_category` | 同 ①④ 口径 |
| 退货（可选扣减） | `order_return` / `return_order_items` | 关联键待验证 |

**已实测关键事实（2026-11-08）**
- `order_detail.sku_code` 值域 1000009~1051040，与 ① 的 `item_id` 同段，可直接关联。
- `order_detail.item_code` 是 1024001~1024245 的另一套内部编码，**不可用于关联**。
- 近 7 日（11-01~11-07）：6,784 个商品码有销量，229,380 件，单均 34 件，中位 10 件，最高 2,151 件。
- 分销结构：≥10 件 3,618 个 / ≥50 件 1,017 / ≥100 件 507 / ≥500 件 47。
- 销量 Top50 中仅 2 个在 ① 售罄名单内 → 卖得火的和已断货的是两拨品。
- 断货持续性（11-03~11-07）：断货次日恢复率仅 0.3%~0.4%；仅 131 个品出现「断 1~2 天后补回并稳定在售」→ 证明 T+1 补货可行，但不能等断了再补。

**数据源限制（必须先确认）**
库里只有订单与库存表，**无浏览/加购/收藏等流量数据**。所以「热度」只能是**销量增速**的代理，对外表述须写「卖得快 / 销量攀升」，不可写「流量热度」。

## 四、口径细则

时间窗：完整自然日，不含今天。近 7 日 = 快照日 T-1 往前 7 个完整日（当前 11-01~11-07）。近 3 日 / 前 4 日为窗内切分。

### 热品池门槛（两表共用）
- **近 7 日销量 ≥ 10 件**（全站中位数，仅用于剔除僵尸品与极端小基数）
- 当日 `is_sold_out=0`（已断的归 ①）
- 10 件是地板；② 内部再按规模分档加严（见下）

### ② 爆卖（两 sheet：按规模 / 按速度，各自分档）

基础算法（两表共用）：
- 逐日销量：按 `sku_code` + 日 聚合 `SUM(quantity)`，得 7 个点
- 近 3 日均 = 最近 3 日合计 ÷ 3；前 4 日均 = 较早 4 日合计 ÷ 4
- **加速比 = 近 3 日均 ÷ 前 4 日均**（前 4 日为 0、近 3 日有量 → 记「新增」）

**Sheet1「规模爆品」— 量大而且在涨**

入表条件：近 7 日 ≥50 件 **且** 加速比 ≥1.5 **且** 上涨天数 ≥3
> 加速比条件不可省。只按规模排会混进「卖得多的老品」，那不是爆。

分档（按近 7 日件数，沿用实测分布）：

| 档 | 近 7 日件数 | 实测品数 | 含义 |
|---|---|---|---|
| **爆款** | ≥500 件 | 47 | 已经卖爆，立刻加推、加采购 |
| **旺销** | 200~500 件 | 137 | 稳定走量，重点盯 |
| **畅销** | 100~200 件 | 323 | 有量，可跟进 |
| **起量** | 50~100 件 | 510 | 刚起量，先观察 |

排序：规模降序 → 同值加速比降序

**Sheet2「速度爆品」— 量不大但涨得陡**

入表条件：近 7 日 10~50 件 **且** 加速比 ≥3.0 **且** 上涨 ≥4 天 **且** 近 3 日日均 ≥5 件
> 小规模必须要求更陡：10 件翻倍是 20 件，采购不值得下单；100 件翻倍是 200 件，才是真需求。

分档（按加速比）：

| 档 | 加速比 | 说明 |
|---|---|---|
| **黑马** | ≥10 倍 | 强势黑马，重点看 |
| **猛涨** | 5~10 倍 | 明显加速 |
| **起势** | 3~5 倍 | 刚起量，苗头 |
| **新品** | 前 4 日为 0 + 连续 3 天递增 + 日均 ≥5 件 | 倍率无意义，单列 |

排序：加速比降序 → 同值按近 7 日件数降序

**命名规避**：①④ 的 A/B/C/D 表示库存价值档；② 完全不用字母，改用中文强度词——
- 规模表：爆款 / 旺销 / 畅销 / 起量
- 速度表：黑马 / 猛涨 / 起势 / 新品

两套档位名不重叠、含义不串，交付说明须注明「② 的档位是热度强度，①④ 的 ABCD 是库存价值」。

### ③ 热品预判缺货
- 日均销量 = 近 7 日件数 ÷ 7；**保守口径取 `max(近3日均, 近7日日均)`**，宁可早报
- 库存 = `SUM(total_qty)` 按 (`item_id`,`provider_id`) 聚合（**必须 SUM 多 zone_code 行，禁止单行覆盖**）
- **可售天数 = 库存 ÷ 日均销量**
- 分级：
  - **P0 可售 ≤ 1 天** → 今天下单（T+1 到货仍可接上）
  - **P1 ≤ 2 天** → 明天必须下单
  - **P2 ≤ 5 天** → 本周安排
  - **P3 ≤ 15 天** → 观察项，默认出表但置灰
- 排序：可售天数升序 → 同值按近 7 日件数降序
- 附加字段：预估断货日（快照日 + 可售天数）、建议下单日（断货日 −1）、是否同时在 ② 爆卖榜

### 通用
- 异常单：单日销量 > 该品其余 6 日均值 5 倍 → 标「异常待核」，排同段末尾，不剔除
- 退货：默认扣减；退货表无法关联 SKU 时降级为不扣，表内注明「未扣退货」
- 两表同源：同一脚本一次计算，同时输出两个文件，③ 的每个商品必须能在热品池中命中

## 六、入口

固定入口维持 4 张：① 卖断货 / ② 爆卖 / ③ 热品预判缺货 / ④ 供货缺货。四个入口对应四个独立文件，不改承诺。

## 七、请 Cursor 重点反向验证的 8 点

1. **`sku_code` 唯一性**：是否恒等于一个 `item_id`，有无一码多品。
2. **多仓库存聚合**：同 (`item_id`,`provider_id`) 是否有多 `zone_code` 行；多行 `SUM` 是否等于真实可售。**（此项最可能让 P0 漏报）**
3. **`total_qty` 语义**：是否为可售量（`sellable_qty`），还是含锁定/占用；含锁定会导致可售天数偏高、漏报 P0。
4. **供商两套体系**：`order_detail.vender_id` 与 `inventory.provider_id` / `item_sale.provider_id` 是否同一套。
5. **订单有效性**：`valid=1` 是否已排除未支付/取消/拆单；`order_time` 为下单还是支付时间。
6. **`quantity` 精度**：`decimal(16,4)` 是否存在称重小数件，取整是否失真。
7. **退货可关联性**：能否关联到 `sku_code` + 退货日期；不能则降级为不扣。
8. **性能**：6,784 个商品码 × 7 日逐日聚合 + 5.5 万行库存聚合，耗时是否可接受（参考 ① 3m30s、④ 3m31s）。

## 八、已知风险

- **加速比对小基数敏感**：三档制已按规模加严（小规模要求 ≥3 倍且涨 ≥4 天），仍可能有噪声，靠「近 3 日日均 ≥5 件」地板兜底。
- **周末效应**：周一跑表时「近 3 日」全为工作日，加速比系统性偏高，建议周一加提示。
- **断码换规格**：老码归零、新码起量会被判「新增」，需人工识别。
- **口径表述风险**：底层是销量增速而非流量热度，交付说明须写清。
- **P0 误报代价**：可售天数依赖 `total_qty` 语义与多仓 SUM，一旦口径错会批量误报或集体漏报，上线前必须用 3~5 个已知商品手工验算。
